# 把模板路径接成一条发布流水线

这次的需求只有一句：我给一个模板路径，你把这段对话整理成符合模板的笔记，写进 Obsidian，同步到 VitePress，最后发到 GitHub Pages。

我一开始打算从零写一个「一键发布」脚本，读了两小时仓库才发现方向错了——站点构建、`git push`、Pages 部署都已经跑通了好几个月，真正空着的只有最前面那一步：AI 整理完的稿子，怎么可靠地落进 vault。

## 先说结论

- 把模板当契约：必需字段和正文章节都从模板文件里解析，换一套模板不用改代码；
- 落库、同步、发布拆成三段，`--publish` 只同步，`--ship` 才提交推送，默认两个都不开；
- 同名文件一律报错退出，覆盖必须是显式选择；
- 站点文章继续由发布脚本生成，不手写 `docs/posts/`，正文只留一份。

## 我是怎么走到这一步的

先看现场，不猜。`package.json` 里已经有 `publish`、`publish:dry`、`ship` 三个脚本；`.github/workflows/deploy.yml` 是 push `main` 触发，用官方 Pages 那两个 action；`docs/.vitepress/config.mts` 里 `base` 写死为 `/vitepress-blog/`，侧边栏是扫 `docs/posts` 下的月份目录动态生成的。也就是说，新文章只要按约定路径出现，导航和归档会自动收录，部署也会自动跟上。

于是问题收敛成一句：怎么把一篇成稿变成 `publish/` 里那个命名规范、字段齐全、可以公开的文件。原来这件事全靠手写，字段靠自觉，同名靠运气——发布脚本默认跳过同名文件，我以为发出去了，站点上其实还是旧版本。

我的第一版方案是把要求写进提示词：反复强调必须有 `summary`、必须有 1200 字。长对话里模型会省掉字段，靠叮嘱不可靠。第二版才换成脚本兜底：读模板的 frontmatter 拿到必需键，读正文里所有 `##` 拿到章节名，再拿成稿逐项比对；缺字段不通过，缺章节只提醒，加 `--strict` 才升级成失败。

## 关键取舍

**只写 vault，不碰 `docs/posts/`。** 站点文件继续由 `publish.mjs` 从 `publish/` 生成。两条路都能写的话，同一篇文章迟早出现两个版本，改的时候一定漏一个。

**开关分成两级。** 写入 vault 是默认就做的；`--publish` 表示顺手同步站点；`--ship` 才做构建、提交、推送。理由很实际：整理错一篇不该顺手推上公网。所以哪怕目标是把整条链路跑通，push 也必须显式加上。

**校验分级，不搞一刀切。** 字段缺失、日期格式不对、标签不在白名单、命中敏感规则，这些是不通过；章节缺失、标题和摘要长度不合适，只提醒。真实写作里章节名经常随内容调整，卡死会让人绕开脚本，那校验就白做了。

**该保留的原文不动。** 仓库里有一篇演示用的假密钥笔记，一直被敏感规则拒绝。它既不能发布，也不能改成「看起来安全」的版本——那样以后就不知道规则真的拦得住什么。最后整篇移进 `90-归档/`，逐字节校验后删掉源文件。

**严格模板装上，但不改默认。** 仓库里那套六段结构的规范包装进 vault 后，和原有的三段式 `发布模板.md` 并存。默认落点仍是「模板名含日记 → `20-日记/`，其余 → `publish/`」，没有趁这次改动顺手改规则。

## 可以直接抄的部分

```powershell
# 只落 vault
npm run note:new -- --template "<模板文件>" --from out.md

# 落 vault + 同步站点
npm run note:new -- --template "<模板>" --from out.md --publish

# 落 vault + 同步 + 构建 + 提交 + 推送
npm run note:new -- --template "<模板>" --from out.md --ship
```

冲突时的输出就是单纯一行报错，不带自动改名的聪明逻辑：

```text
✗ 目标笔记已存在，未覆盖：publish/2026-11-12-vault-publish-pipeline.md
  换一个 --slug、用 --date 指定别的日期，或确认后加 --force。
```

适用条件：vault 路径已通过 `publish.config.json` 配好；模板 frontmatter 的键就用作者需要的字段，脚本不额外发明字段。

## 踩过的坑

**把目录当模板传。** 第一次用 `--template _模板`，脚本直接退出并列出目录里的两个模板。这比自动挑一个更省事——挑错模板的返工成本比再敲一次路径高。

**日期写成 `2026/11/12`。** 大白话里常见，但 frontmatter 要求 `YYYY-MM-DD`，而且必须是真实存在的日期。校验里单独判了 `2026-02-30` 这种，不然 `new Date` 会悄悄帮你进位。

**同名文件不报错。** 这是最隐蔽的一个：发布脚本默认跳过已存在的目标文件，正因如此，`note:new` 把冲突挪到了写入前。不改发布脚本的行为，只在前面加一道硬拦。

**`Move-Item` 被拒绝访问。** 归档那篇演示笔记时，PowerShell 的 `Move-Item` 报 `UnauthorizedAccessException`。改用 Node 复制到目标、逐字节比对内容一致、再删源文件，三步走，避免半途失败留下两份同名笔记。

**模板里的自查提示块被发上站。** `发布模板.md` 末尾有一段 `::: tip 发布前自查`，是写给作者看的。第一次演示发布时它原样渲染在页面上。现在写入 `publish/` 时会把这一段剥掉，其它 tip 块不动。

**无关笔记让退出码变成 1。** vault 里还有别的文件被敏感规则拒绝时，发布脚本整体退出码就是 1。没有改这个约定——CI 靠它发现异常。只在 `--publish` 之后的输出里写清楚：站点已同步，但有别的笔记被拒绝，所以没有继续发布。

## 收尾

这套东西只解决「已经有成稿」之后的事。整理本身还是 AI 写、人来复核，脚本能保证的是不走样：字段齐、落点对、敏感内容进不来、同名不覆盖。

下一步想把「模板 → 目录」的映射也挪进配置，这样连 `--dest` 都不用记。再往后才是真正省时间的部分：把「哪段对话值得写」也变成可执行规则，而不是每次靠感觉。
